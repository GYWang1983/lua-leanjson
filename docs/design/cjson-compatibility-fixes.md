## 逐项说明

### F01：数字编码精度范围、设置返回值

- **原问题：** `encode_number_precision` 只接受 1–14，设置成功后返回旧值。
- **证据：** `agentzh.t:TEST20` 请求精度 16 时失败；`test.lua:L420` 设置 3，目标返回 14；`test.lua:L424` 设置 14，目标返回 3。后两项原始差异受 setup 依赖影响而归入 unsupported，仍有实际返回值证据及源码佐证。
- **已实现：** 支持 1–16，setter 返回新值；支持范围内的数值字符串和小数截断。普通数值、整数 double、负零及 proxy 写入值使用指定精度；原文数字 token 保留原字节，reader 固定构造时格式。
- **已验证：** 1/3/14/15/16、非法值、额外参数、getter、失败不修改设置、`2^53` 输出、正常／safe 实例隔离和九格输入。`test.lua:L420`、`L424`、`L431`、`L439`、`agentzh.t:TEST20` 通过。超范围与非有限配置值按声明范围拒绝，不模拟 C 整数溢出。

### F02：稀疏数组配置参数校验

- **原问题：** `encode_sparse_array("not quite on")` 把该字符串视为开启转换。
- **证据：** `test.lua:L487`；实现位于 `lua/leanjson/table.lua`。
- **已实现／验证：** convert 接受布尔与精确 `on/off`，ratio/safe 支持数值字符串、小数截断及 0–2147483647；拒绝未知选项、额外参数及非法数值。`test.lua:L487` 通过；无效调用前后 getter 不变，普通 table、proxy 赋值与 reader 使用真实配置策略。
- **有意边界：** 按本清单要求保持失败原子性；原生实现会在后续参数报错前先更新前面的参数，不复刻这一副作用。非有限值和超范围数值直接拒绝，不复刻原生 NaN／溢出转整数结果。lazy 内部空洞仍属 F18。

### F03：独立配置实例 `new()`

- **原问题：** 缺少 cjson 形状的实例工厂；编码设置存储在模块共享状态中。上游依赖 `new()` 的 helper 失败，使多项后续检查失去有效前提。
- **证据：** `test.lua:L404`、`L412`、`L495` helper；`agentzh.t:TEST16`、`TEST17`、`TEST18`。
- **已实现：** `leanjson.new()` 返回独立编解码器；每次创建使用库默认配置，不继承父实例当前值。`encode_number_precision`、`encode_sparse_array` 使用实例闭包，默认模块和兄弟实例互不污染，不切换全局状态。null/数组标记共享。
- **已确认语义：** 用户明确保留 lazy／eager／preload 与内存／文件／增量输入；`new()` 不创建 JSON 文档，也不强制 eager。显式编码使用调用实例；reader 创建时固定数字格式；未修改的原文片段保持原样。lazy 写入、子视图及 decoder 输出保留创建实例，`codec.fork` 为分支采用调用实例。具体时机见 [README](../../README.md#independent-codec-instances)。
- **验收：** 覆盖默认模块、两个实例、嵌套 `new()`、失败设置不改变配置、跨实例编码／fork／reader、子视图脱离、增量 get／finish、重入及协程让出，九种输入／加载组合保持有效。safe 实例隔离已在 F04 补充联验。
- **验证记录：** [F03 验证报告](../verification/f03-codec-instances.md)。F01/F02 的参数及返回值差异未在本项修改，其余缺口继续逐项处理。

### F04：safe 模块及错误返回契约

- **原问题：** 没有与 `cjson.safe` 对应的模块、`encode`、`decode`、`new` 契约。
- **证据：** `test.lua:L501`、`L504`、`L512`、`L515`；`agentzh.t:TEST18`。
- **已实现：** `require "leanjson.safe"` 及 `safe.new()` 使用独立普通 codec，并仅保护转换／源构造。成功返回一个值；转换错误返回两个值 `nil, err`，保留 false 和共享 null。`decode(nil)` 属于受保护的输入类型错误；缺少／多余参数与配置 setter 错误直接抛出。数字输入沿用 cjson 的字符串转换语义。
- **LeanJSON 扩展：** `decode(raw[, opts])`、`decode_file(path[, opts])` 接受加载选项；非法选项在保护调用外校验。`new_decoder([opts])` 的源构造错误返回错误对。decoder／reader 方法、辅助函数及 lazy 属性访问保持原有契约，不承诺将后续错误全部转换为错误对。
- **已验证：** 成功值、JSON null、false、返回数量、语法／参数错误、safe.new 默认配置与隔离、已有标记、九种加载／输入组合、文件扫描与增量失败后的无 GC 资源释放。上游适配器已调用真实 safe 模块并保留 feed／finish 错误对。[F04 验证报告](../verification/f04-safe-codecs.md)记录实际结果。
- **保留边界：** 已支持功能的精确错误文本已由 F17 对齐；F01/F02/F05 见对应项。Lua 保护调用没有暴露原生 C 包装器的 `LUA_ERRMEM` 分类，本项不宣称 VM 内存耗尽行为完全一致，也不靠错误字符串猜测该状态。

### F05：数组／空表标记和配置

- **原问题：** 缺少 `empty_array`、`array_mt`、`encode_empty_table_as_object`、`decode_array_with_array_mt`。
- **证据：** `agentzh.t:TEST2`–`TEST4`、`TEST7`–`TEST15`；不能把现有 `empty_array_mt` 一并说成未实现。
- **已实现／验证：** 共享且区分两种 metatable 与空数组 sentinel。显式 `array_mt` 使用 raw 长度／值并忽略 hash，`empty_array_mt` 先执行稀疏策略。两个配置均隔离于实例，支持布尔／on/off 和参数检查；eager 默认不添加标记，开启后为所有数组添加 `array_mt`。source 创建时固定策略，增量 get／重复 finish 及延迟子视图均保持该策略。
- **保留差异：** lazy/preload 默认继续保留 JSON 容器类型与原字节，不把源 `[]` 改写为 `{}`。开启标记时通过私有 metatable 暴露公共 marker；不通过物化绕过 proxy 的 F18 修改限制。因此 TEST12/13/14 在 eager 下通过，在 lazy/preload 中仍有明确行为差异；不能宣称九格全部 cjson 等价。
- **验收记录：** [F01/F02/F05 验证报告](../verification/f01-f02-f05-config-arrays.md)，包含 raw marker 优先级、正常／safe 九格、配置快照及资源回归。

### F06：外部数组代理编码

- **现状：** 对上游通过 `__len`、`__index` 提供元素的外部数组代理编码，输出 `{}`，基线输出 `["foo","bar","baz"]`。
- **证据：** `agentzh.t:TEST23`，是未受 setup 失败影响的独立差异。
- **修复目标：** 对齐基线识别这类对象并读取数组元素的规则；与 LeanJSON 自有 proxy 的原始片段编码路径区分。
- **验收：** 原用例通过；补充空数组、嵌套元素、元方法异常、非法长度和循环引用，确保错误可控且不影响普通对象编码。

### F07：最大嵌套深度配置

- **原问题：** 缺少 `decode_max_depth`、`encode_max_depth`；索引深度不能代替合法嵌套深度，原文片段编码还会绕过限制。
- **已实现：** 两个独立配置默认 1000，范围 1–2147483647，支持 getter、新值返回及原生参数校验。source／decoder 固定创建时 decode 限制；非零 `opts.max_depth` 为单次覆盖。reader 固定 encode 限制，并在 length／首次 next 校验普通 table、修改节点和原文片段的实际输出深度。
- **深度范围：** source v2 不再截断至 4096；重扫、eager rebuild 与按需读取继承源策略。legacy `parse`／source v1 保持原有上限。编码、赋值快照、物化与依赖遍历使用显式栈，已执行实际 5000 层输入，不能只以 setter 返回值证明支持。
- **验收：** 对象／数组／混合容器边界、循环、非法参数、配置隔离、原文片段迁移后的祖先深度、keep_origin、九格输入及错误后的清理。详见 [F07/F17 报告](../verification/f07-f17-depth-diagnostics.md)。

### F08：非标准数字解码

- **原问题：** 缺少 `decode_invalid_numbers`，不能读取原生支持的十六进制、前导零、Inf/Infinity/NaN 等形式。
- **已实现：** 用户确认默认对齐 lua-cjson。配置默认 true，接受布尔与 on/off；策略固定于源创建时并传递到重扫、延迟字段及 eager rebuild。支持带符号的小数、hex float、NaN payload 和超大指数；纯十进制整数使用原生 signed64 饱和值，整数 `-0` 与浮点 `-0.0` 按原生语义区分。
- **明确边界：** `decode_invalid_numbers(false)` 使用 RFC 数字语法，不复制原生 strict 分支仍接受尾随小数点／带符号 `.5` 的细节；C source 零模式与 legacy parse 保持原有严格语法。未修改的有限源数字继续保留原文拼写。精确异常文本仍属 F17。
- **验证：** 上游 `test.lua:L220`–`L257`、独立原生对照和九格联验；完整矩阵中受 F07 深度 reset 依赖阻挡的记录保持 unsupported，另执行未经改写的上游相关用例切片，不能把切片结果冒充完整矩阵通过。见 [本轮报告](../verification/f08-f09-f11-f12-numbers-bytes.md)。

### F09：非有限数字编码

- **原问题：** 缺少 `encode_invalid_numbers`。
- **已实现／验证：** 默认 false 拒绝；true/on 输出 `NaN`、`Infinity`、`-Infinity`；null 模式输出 `null`，off 关闭。覆盖根值、普通 table、proxy 写入、数值对象键和未修改源容器中的非有限数字。reader 固定构造时配置，原文片段不能绕过策略。
- **内存边界：** native flags 标记非有限浮点 token，编码只需读取其有界前缀；不会拼接长 NaN payload 或超长饱和整数。全量／分块编码保留原生正 Infinity 键的稀疏数组判定；开启稀疏转对象后才进入键编码。错误文本仍属 F17。

### F10：JSON 注释解析开关

- **现状：** 缺少 `decode_allow_comment`；开启注释的基线用例成功，当前仍拒绝。
- **证据：** `test.lua:L337`–`L360`，含单行、多行、连续注释、冒号前后注释、未闭合注释及数字内部注释。
- **修复目标：** 对齐开关行为；字符串内部的 `//`、`/* */` 不得被当作注释。
- **验收：** 原用例、关闭开关后的拒绝、换行形式及注释定界符跨 feed 分片；明确保留原始片段时的输出处理，避免仅扫描接受、后续访问或输出失败。

### F11：非 UTF-8 字节字符串

- **原问题：** 上游 all-octets 解码被 UTF-8 校验拒绝。
- **已实现／验证：** 默认字节兼容，原样返回 0x00–0xff 对应的合法 JSON 字符串内容，包含原始高位字节及对象键；不做有损替换。内存／文件／增量输入与 lazy/eager/preload 共享策略，重复字节键按解码后键取最后值。
- **严格开关：** `decode_validate_utf8(true)` 要求合法原始 UTF-8。两种模式都校验 Unicode escape、surrogate 配对及未转义控制字节。已有严格 JSONTestSuite 用例显式开启数字与 UTF-8 严格设置，保留全部原断言。

### F12：字符串转义及正斜杠配置

- **原问题：** 缺少正斜杠配置，all-octets 编码未转义 `/` 与 DEL。
- **已实现／验证：** `encode_escape_forward_slash` 默认 true；布尔／on/off 可切换。DEL 始终输出 `\u007f`，其他高位字节原样保留。字符串值、对象键、proxy 新值与包含 slash/DEL 的源字符串均执行配置；源字符串按有界块解码／转义，keep_origin 不能绕过策略。
- **原文边界：** 不涉及 slash/DEL 的未修改源字符串仍保留既有原始 escape，而非强制整体 canonicalize；修改后字符串按当前配置重新编码。所有编码设置在 reader 创建时固定。详见 [本轮报告](../verification/f08-f09-f11-f12-numbers-bytes.md)。

### F13：编码缩进配置

- **现状：** 缺少 `encode_indent`；基线期望缩进输出的用例得到紧凑 JSON。
- **证据：** `test.lua:L363`–`L395`，包括空结构、嵌套对象／数组、数组内对象及非空白缩进字符串 `abc`。
- **修复目标：** 对齐支持的缩进值、getter/setter 和格式；不能擅自把上游接受的非空白缩进选项过滤掉。
- **验收：** 原用例输出及配置恢复；对原始片段与修改片段确定统一的格式规则，不能通过整棵物化来掩盖代理路径缺口。

### F14：跳过不支持的值类型

- **证据：** `agentzh.t:TEST22`。
- **修复目标：** 按基线区分配置开启／关闭时不支持类型的处理规则，不自行推断为全部转 `null` 或全部删掉。
- **验收：** 原用例；补充根值、对象成员、数组元素及嵌套结构的结果，确认数组索引、错误传播、实例设置和资源释放。

### F15：编码缓冲区保留配置

- **现状：** 缺少 `encode_keep_buffer`，上游 setter/getter 和参数校验用例无法执行。

- **待确认：** 当前 Lua/Rust 编码和分块输出架构如何对应保留／释放缓冲区语义，尤其是大请求处理后的内存留存。
- **修复目标／验收：** API 形状和参数行为对齐；缓冲区生命周期必须有真实实现与可观察证据，不能只存一个布尔值假装支持。联验连续大／小编码、不同实例及清理后的内存表现；本次功能矩阵本身不能证明内存目标。

### F16：模块身份与版本字段

- **现状：** 缺少测试读取的 `_NAME`、`_VERSION`。上游身份断言针对 cjson 的名称及版本。
- **证据：** `test.lua:L94` 模块身份断言；报告记录了定义及读取阶段的缺失字段。
- **待确认：** 对项目真实名称 `leanjson` 和真实版本提供元信息后，身份字段的测试应采用什么明确的项目适配规则。
- **修复目标／验收：** 保持 LeanJSON 品牌与实际版本，不能伪造为 cjson 的版本以获得通过；普通模块、new 实例、safe 模块的字段完整且一致。身份名称不同与 API 缺失分别记录，测试适配必须显式披露。

### F17：异常消息与位置格式

- **原问题：** 语法错误只有通用 parse error，缺少原生期望项、token 分类和准确位置；编码及参数错误也有自定义文本。
- **已实现：** source v2 的伴随 tokenizer 记录有界 token 状态和嵌套上下文，按原生顺序完成意外 token 的分类，覆盖结构错误、数字前缀回退、字符串／Unicode escape、代理对、UTF-16/32 检测、深度和跨 feed 全局位置。原始机器诊断 `code/detail/offset` 保留，公开文本由新增 C formatter 提供；成功后释放诊断工作区。
- **已验证：** 普通／safe 的参数数量、输入类型、非法值／键、NaN/Infinity、稀疏数组、循环及深度错误；上游原定义不改写。另以独立原生对照语法探针和全部分片点验证位置；详见 [F07/F17 报告](../verification/f07-f17-depth-diagnostics.md)。
- **边界：** 未实现的注释／其他配置仍按原缺陷编号记录；不能将其标成兼容通过。严格 RFC 数字、UTF-8 扩展及控制字节／嵌入 NUL 的较严格拒绝，与原生接受输入的情况保持显式差异。LeanJSON 的 opts、reader／decoder 和代理操作扩展保留自身错误契约；不承诺 VM OOM 或平台调用栈限制下的错误完全相同。

### F18：lazy 代理与普通 Lua table 的操作边界

- **现状：** 原生 `next`、`rawget`、`rawset` 绕过代理；第三方编码器可能不识别代理。项目提供访问／遍历辅助函数和 `materialize`；`lazyload=false` 返回普通值。此项来自已有 API 设计边界，不是主矩阵中的 14 项独立失败之一。
- **证据：** [迁移文档](../migrating-from-cjson.md)、[proxy API](../source-proxy-api.md)；与 F06“由 LeanJSON 编码外部代理”是不同方向的问题。
- **待确认：** 哪些调用要求在 lazy 模式保持透明，哪些通过 eager/materialize 作为适配边界。原生 raw 操作不触发元方法，不能承诺仅改 Lua proxy 即可完全兼容。
- **修复目标／验收：** 对批准的兼容边界分别测试原生操作、辅助 API、第三方编码、修改后的输出与资源生命周期；不得全局替换 Lua 内置函数或悄悄全量物化来获得表面兼容。

## 修复次序建议

1. **配置基础及直接行为：** F03 → F01/F02 → F04，优先消除共享配置和 setup 依赖导致的测试阻塞。F01/F02 如先修，必须在 F03 完成后补验实例隔离。
2. **数据形状与输出：** F05/F06/F07 → F09/F12/F13/F14；明确 proxy、普通 table 和原始片段的共同规则。
